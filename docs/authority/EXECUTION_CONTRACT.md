# Optimatrix Execution Contract

**Status:** ACTIVE EXECUTION AUTHORITY

Every imperative is a gate. An unmet gate prohibits a completion claim.

## Before editing

- Read the Authority route, the one active task, owning contracts, code path, tests, manifest, and
  lockfile.
- Establish the active task's canonical `SessionDecisionUnit` baseline, denominator, earliest
  material blocker, expected product delta, durable-data effect, and legacy-data effect.
- Resolve decision-critical ambiguity from source evidence or one focused question.
- Search existing code and locked dependencies before adding or replacing an implementation.
- For non-mechanical choices, inspect project precedent and a mature same-problem primary source.
- Verify version, compatibility, market-source, runtime, and data claims from current evidence.
  Prior reports and green CI are leads, not proof.

## Decision order

1. Reuse a fitting audited new-product implementation or calculator.
2. Use a compatible maintained dependency or established pattern.
3. Write the smallest direct implementation only when a verified constraint prevents the first two.

Do not reuse obsolete V2 strategy semantics merely because their code exists. A new dependency must
reduce final complexity and have verified compatibility, maintenance, license/security, and a locked
version.

## Change and cleanup

- Map every abstraction, configuration field, flag, file, dependency, and durable fact to a current
  active-task criterion.
- Build nothing for hypothetical Channels, callers, scale, migrations, or failures.
- Prefer direct code, current style, and focused tests.
- Keep no parallel old/new strategy path, hidden compatibility translator, or legacy Case reader.
- Remove code, tests, docs, configuration, and artifacts made obsolete by the same change.
- Preserve unrelated human work and search references before deletion and completion.
- Update manifests, lockfiles, and generated outputs only through their canonical workflow.
- Leave no commented-out, temporary, duplicate, or “just in case” path.

## Product truth during implementation

- One `SessionDecisionUnit` remains the funnel unit; do not count legs, candidates, retries, or rows.
- Required missing or stale facts remain `UNKNOWN`; do not replace them with zero, calm, or neutral
  defaults.
- One selected attempt remains four-leg coherent; do not synthesize `FULL_ENTRY` from independent
  component attempts.
- Partial short exposure enters remediation, never normal carry.
- Eligibility dimensions remain separate; do not make UI convenience change Outcome truth.
- No target file, fixture, environment default, or generated output may reference the legacy V2 Case
  root as a new-product root.

## Verification and completion

- Verify at the correct layer. Unit tests do not prove product, live-market, persistence, runtime,
  qualification, or profitability behavior.
- Run the active task's focused tests, full repository gate, deterministic business scenarios,
  compilation/build checks, and final reference/diff inspection.
- Use at most the live action expressly authorized by `CURRENT_STAGE` and the active task. A failed
  or consumed authorization grants no retry.
- Back external claims with current evidence or primary sources. Report unavailable checks exactly
  and leave that layer unverified.
- Inspect final files, references, manifests, lockfiles, task linkage, legacy-root absence, and
  obsolete residue.
- Report the business delta first, then exact checks, cleanup, and gaps.

Engineering checks satisfy only their declared implementation layer. Product completion comes only
from direct observation of the active task's user-visible or funnel delta. Tests, scenarios,
manifests, archives, and green CI alone never satisfy the task.
